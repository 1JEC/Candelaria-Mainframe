# Leads Agent — Decisions Log

Branch: `leads-agent`. Started 2026-08-13. Format: `ASSUMPTION` (undocumented choice, most conservative option, kept working), `LIMITATION` (honest reduced version, logged, moved on), `V2 CANDIDATE` (tempting extra, deferred).

## Phase 0 — Repo inventory (read before building anything)

Full inventory was done via a repo-exploration pass. Key findings that change how this feature is built vs. a blank-slate reading of the spec:

- **Hosting is Netlify, not Vercel.** `netlify.toml` exists and configures `functions = "functions"`, `publish = ".next"`. No `vercel.json`. `.vercel/project.json` exists but appears stale/unused. `ASSUMPTION`: build against Netlify's Next.js runtime. Netlify Functions have their own execution-time limits (background functions support up to 15 min on paid tiers vs. the default ~10s/26s synchronous limit) and Next.js's `after()` from `next/server` is a Vercel-optimized primitive with uneven support elsewhere. `LIMITATION`: I will not assume `after()` reliably schedules a next tick post-response on this host. The run/worker split (§8 of the spec) is built as: a client-side poller calls `/api/agents/leads/worker` repeatedly (every ~2s) while a run is `running`, each call claims and processes one bounded batch and returns. This keeps every invocation short and synchronous, sidestepping the Netlify background-function question entirely, at the cost of the run depending on a client (browser tab or the sweeper cron) staying around to keep ticking it forward — exactly the gap the spec's own sweeper design anticipates. The sweeper cron route restarts stale runs the same way regardless of who was ticking them.
- **This is not a blank slate — extend `MODULE D: LEAD-ENGINE` in `drizzle/schema.ts`, don't create a parallel schema.** Existing tables: `leads`, `leadEvents`, `prospectSources` (1:1 with leads — a design smell but out of scope to fix), `outreachTasks`, `outreachMessages` (unused by any UI today, but shaped like the spec's `messages` table), plus `agentRuns` (cost/usage logging per AI call — closest analog to `ai_usage`) and `settings` (has `outreachApprovalRequired`, `suppressionListDomains`, `suppressionListEmails` array columns — today's suppression mechanism). `ASSUMPTION`: `outreachMessages` becomes the `messages` table from §9 of the spec (extended with columns, not replaced); a dedicated `suppression` table is added because array columns on a singleton `settings` row can't carry `source_url`/`reason`/`created_at` provenance per §4 rule 1, and AVG rule 10 (`forget` leaves a one-way hash) needs a real table with its own primary key.
- **`lib/agents/prospector.ts` is an orphaned stub, not working prospecting.** It makes one raw Anthropic call asking the model to *invent* 3 companies as JSON — no real data source, `options.limit` is accepted but never used, `estimatedCost` is hardcoded rather than computed, and nothing in the app calls this function (no route, no cron, no UI button). This directly violates the master spec's absolute rule "never invent companies... every scoring signal is reproducible from stored evidence." `DECISION`: this file is replaced by the real OSM-first discovery pipeline; it is not extended, because extending a hallucination generator would mean shipping fabricated leads into a real leads table used by a real business. The model string it and its two siblings (`email-triage.ts`, `content-generator.ts`) use, `"claude-opus-4-7"`, is not a real current model id — flagged, not fixed in those two unrelated files (out of scope), but the new shared AI wrapper uses real current ids (`claude-haiku-4-5-20251001`, `claude-sonnet-5`).
- **No component library exists** — just three CSS utility classes (`.btn-primary`, `.btn-secondary`, `.input-field`) plus hand-rolled markup per page (`components/ui/Modal.tsx`, `ConfirmModal.tsx`, `Pagination.tsx`, `SearchFilterBar.tsx`, `Toast.tsx` are the only shared pieces). No dark mode is implemented anywhere (`ASSUMPTION`: do not introduce one for this feature — matching the spec's "reuse, don't introduce new tokens" instruction literally means staying in the existing light-only, `bg-gray-50` shell). `DECISION`: new shared primitives this feature needs and the app lacks (`DataTable`, `StatusBadge`, `StatCard`, `EmptyState`) are added to `components/ui/` in the exact visual idiom of the existing 5 files (same border/radius/spacing choices), since the spec explicitly allows new primitives "only when nothing fits, built in the style of their neighbours" — a live console feed and an evidence table are things nothing existing fits.
- **Auth has two roles only** (`user`, `admin`), enforced today only via one inline page-level check, never via a reusable helper or role-gated API route. `DECISION`: introduce `lib/auth-guard.ts` with a `requireAdmin()` helper (the spec's owner/admin gating collapses to `admin` here, since there's no `owner` role in this app) and use it on every new mutating route. `ASSUMPTION`: "owner or admin" in the spec = "admin" in this app.
- **No rate limiter exists anywhere.** `DECISION`: build a minimal in-DB token-bucket-style limiter (reusing the pattern of counting recent `auditLog`/`agentEvents` rows in a time window) rather than pulling in a new dependency — matches "reuse the repo's limiter" in spirit (there isn't one to reuse, so a small one is added under `lib/rate-limit.ts` and treated as the thing future features reuse).
- **Migration workflow**: no `drizzle/migrations/` folder exists; `db:push` (schema-diff push, no committed SQL) is the only workflow actually exercised so far. `ASSUMPTION`: continue with `db:push` rather than introducing generated migration files for this feature alone — switching the whole repo's migration strategy is out of scope of a single feature branch.
- **Missing local secrets**: `.env.local` has Postgres/Neon/Vercel-blob vars only — `ANTHROPIC_API_KEY`, `RESEND_API_KEY`, `NEXTAUTH_SECRET`, `INTAKE_API_KEY`, `GOOGLE_PLACES_API_KEY`, `KVK_API_KEY` are all absent locally (likely set in Netlify's dashboard for production, not synced to this checkout). Every adapter/AI call in this feature is written to disable itself gracefully and report via `doctor` when its key is missing, per spec — this was going to be necessary regardless, and is doubly necessary given the local environment already lacks most keys.

- **CSV seed** (`csv-seed.ts`) — real, unit-tested (not just typechecked): a small hand-written CSV line parser (no dependency — handles quoted fields with embedded commas), minimum `name` OR `website` per row enforced, falls back to the domain as the display name when only a website is given. `DECISION`: doesn't fit the `DiscoverySource.discover(city, sector)` shape (a CSV upload isn't a city/sector query) — registered in the source list as a visibility no-op, with `parseCsvSeedRows()` as the real entry point the Phase 6 upload UI will call directly.

## Phase 3 — Crawler, contact extraction, audit signals (done)

- **New dependencies added**: `robots-parser`, `libphonenumber-js`, `cheerio` — all three named or clearly implied by the spec (§4 rule 12, "Contact extractor... phone via libphonenumber-js NL"). Hand-rolling robust HTML parsing/phone validation via regex would have been the actual scope-creep here; these are small, well-established, no native binaries.
- **`crawler/robots.ts`** — real `robots-parser` integration, verified directly (not just typechecked): fed synthetic `Disallow: /` and `Disallow: /wp-admin/` robots.txt text through it and confirmed both the "everything blocked" and "one path blocked" cases resolve correctly against our UA string. A robots.txt fetch/parse failure means "no rules found" → allowed, never a false block.
- **`crawler/fetch-page.ts`** — the actual page fetcher: robots-checked, `page_cache`-backed (30-day reuse, matching the lead-level audit-staleness threshold), per-host politeness (≥1500ms between requests to the same host) and global concurrency (≤5) enforced via in-process trackers. `LIMITATION`: politeness is per-Node-process only, not cross-invocation — logged as adequate for how Phase 6 will actually dispatch work (one domain per task), not a general-purpose distributed rate limiter. `ASSUMPTION`: the 2MB response cap is enforced by a `Content-Length` pre-check plus a post-fetch character-count truncation, not exact byte-streaming — `fetch()` has no built-in byte cap and full streaming enforcement wasn't worth the added complexity for what's a safety net, not a hard requirement.
- **`crawler/index.ts`** — `crawlDomain()`: homepage + site-expansion contact/team URLs (Phase 2), deduped, capped at the 8-page budget.
- **Verified live end-to-end** against two real websites found via the OSM adapter in Phase 2 (not just typechecked): one had an **expired SSL certificate** — the crawler correctly failed the fetch and the audit correctly reported `httpsValid: false` rather than silently skipping the signal. The other (a real dental practice site) produced a fully real, correct result: real email, real E.164 phone number, real Instagram/Facebook links, `schema.org` type `LocalBusiness` detected from real JSON-LD, Google Analytics + GTM detected, mobile viewport true, HTTPS valid, a real measured load time (median of 3 live fetches), and a 5-link broken-link sample all returning 200.
- **Bug found and fixed during that live test**: `libphonenumber-js`'s default `findPhoneNumbersInText` (and even the "max" build's `parsePhoneNumberFromString`) threw `Cannot read properties of undefined (reading 'hasOwnProperty')` when called through this app's actual module graph — reproducible every time through `crawlDomain()`, but not in an isolated one-line repro. Root cause not fully chased down (looked like the convenience builds' internal metadata wiring breaking under this project's specific module resolution), but the fix is clean either way: import `libphonenumber-js/core` and pass `metadata.max.json` explicitly rather than relying on the convenience build's implicit state. Verified working after the fix.
- **Bug found and fixed**: `audit.hasContactForm` only checked the homepage's HTML, while `contacts.hasContactForm` (Phase 2/3 extraction) correctly checked every crawled page — on the real test site, the actual contact form lived on `/contact-inschrijfformulier-`, not the homepage, so the two signals disagreed (`true` vs `false`) until fixed to check all crawled pages consistently. Caught because the two independent code paths were compared side by side during live testing, not from a spec reread — a concrete argument for the "run it, don't just typecheck it" verification standard applied through this phase.
- **Audit module** (`audit/index.ts`) covers the subset of spec §6's audit fields that are honestly measurable from crawled HTML/HTTP responses without a paid API: `https_valid`, `http_status`, `load_time_ms` (median of 3 real uncached fetches), `mobile_viewport`, platform fingerprint (`audit/platform.ts` — WordPress/Wix/Squarespace/Shopify/Webflow/Joomla/Drupal pattern matching, reports nothing rather than guessing when no pattern matches), title/meta/h1 presence+length, `schema.org` types (real JSON-LD parsing), analytics/pixel detection (GA/GTM/Meta Pixel/Hotjar/Clarity signatures), `has_contact_form`/`has_chat_or_whatsapp`/`has_online_booking`/`has_webshop` (keyword/link heuristics — `hasOnlineBooking`/`hasWebshop` in particular are heuristic pattern matches, not certain), a 5-link broken-link sample, image/alt-text counts, and an approximate "last content year" guess from a footer copyright-year regex (explicitly a guess, not a real content-freshness measurement — footer copyright years are frequently stale on real sites regardless of actual last-updated date).
- **PSI (PageSpeed Insights)** (`audit/pagespeed.ts`) — gated on `PAGESPEED_API_KEY` (unset here, untested live), disables itself gracefully.
- **Not implemented, logged as `LIMITATION`** (spec §6 fields not covered by this phase): `contact_person` extraction (name/role from a team page) — generic, reliable extraction across arbitrary site layouts is genuinely hard and a sloppy attempt would risk inventing/misattributing a person's role, which the spec's integrity rules explicitly forbid; opening hours extraction — same reasoning, too layout-dependent to do reliably in one generic pass; exact image weight in bytes — would require fetching every image on every page, a meaningfully larger crawl budget for a signal that mostly correlates with load time (already measured directly); headless-browser fallback for JS-rendered pages (§4 rule 14) — no headless browser runtime is set up for this deployment target (Netlify Functions don't have a Chromium binary available without a separate heavy dependency like `@sparticuz/chromium`), so pages that render entirely client-side will show up as thin/empty rather than being retried with a real browser. All four are real gaps against the spec, not corners cut silently — each is a concrete `V2 CANDIDATE`.
- **Architectural boundary**: Phase 3 ships pure functions (`crawlDomain`, `mergeContactExtractions`/`toContactFields`, `runAudit`) with no database writes into `lead_contacts`/`lead_audits` — those tables get populated by Phase 6's run orchestration, which owns the `leadId`/`runId` context these functions don't have. `page_cache` writes are the one exception (that's the crawler's own cache, not lead data).

## Phase 4 — Scoring rubric engine (done)

- **`scoring/signals.ts`** implements every §7 fit/pain line item against real Phase 3 output (`AuditRaw`/`ExtractedContacts`), each producing a `ScoredSignal {code, labelNl, evidence, sourceUrl, points}` — only pushed when there's real evidence; absence of a problem/fit-match contributes silently (0), matching "unevidenced signals score 0" without emitting phantom rows.
  - `size_match` (spec: "size 2-50 or premises+team page") — no real employee-count data exists from the free sources this pipeline uses, so this is evidenced only via the spec's own OR-clause: a crawled team/over-ons page. `ASSUMPTION`, logged in the code.
  - `active_business` uses "working phone found" + "content not obviously stale" as the proxy for the spec's own vaguer "active business (recent content, working phone)" — both measured facts, not guesses.
  - `broken_webshop` deliberately **conservative**: only fires when the crawl's own 5-link broken-link sample happened to include a cart/checkout URL that came back non-200. It will under-detect (a real broken checkout not in that small sample scores 0) rather than infer "broken" from webshop-presence alone, which would be scoring an unmeasured guess.
  - `outdated_platform` required a real fix mid-build: the check needs raw HTML, which only exists inside the audit module, not in the scoring layer — moved `detectOutdatedMarker()` into `audit/platform.ts` (flash/frameset/ancient-jQuery/FrontPage markers, same "only fires on an unambiguous pattern match" discipline as `detectPlatform`) and added `outdatedMarker`/`outdatedMarkerEvidence` fields to `AuditRaw`, rather than leaving a stray dead-code placeholder in signals.ts that I'd initially written and caught on review before ever running it.
  - `seo_basics_broken` (spec: "title/meta/h1, 3 each, 9 total") implemented as three separate 3-point signals (`seo_title_missing`/`seo_meta_missing`/`seo_h1_missing`) rather than one all-or-nothing 9-point check — matches the spec's own "3 each" wording.
  - `no_chat_or_booking` applies uniformly across sectors rather than a real per-sector expectation table (spec says "where the sector expects it"). `ASSUMPTION`: building an accurate per-sector expectation matrix is a real judgment call beyond this phase's scope — logged rather than guessed at.
- **`scoring/index.ts`**: `scoreLead()` sums signals (fit capped 40, pain capped 60, total capped 100), applies the exact priority thresholds (A≥70, B 55-69, C 45-54) and the "fit < 18 disqualifies regardless of pain" rule verbatim (strict `<`, confirmed `fit === 18` does NOT disqualify — verified directly, see below). `recommendedOffer`/`recommendedChannel` derivation is a documented `ASSUMPTION` (the spec defines the rubric precisely but not an exact offer-recommendation algorithm) — mapped against Candelaria's real service ladder from the global `CLAUDE.md`, never price-led.
- **Verified live end-to-end**, not just typechecked: ran discovery → crawl → extract → audit → score across three real cases using the same real sites from Phase 2/3 testing:
  - A healthy site (working HTTPS, forms, booking, analytics, schema.org) scored fit=29/pain=0/total=29, correctly **not qualified** (below the 45 minimum) — a well-built site is genuinely not a good outreach lead, and the engine agrees.
  - The site with the expired SSL certificate (found in Phase 3) scored fit=18/pain=60/total=78/**priority A**/qualified — exactly the intended outcome for an unreachable/dead site.
  - A synthetic "no website found" candidate scored identically (fit=18/pain=60/total=78/priority A) via the same `no_website` path.
- **Architectural boundary, same as Phase 3**: `scoreLead()` is a pure function — no writes to `lead_signals`/`leads.fit_score` etc. Phase 6's orchestration owns turning a `ScoringResult` into DB rows against a real `leadId`.
- **Verification**: `npx tsc --noEmit` and `npm run build` both clean. Live 3-case test run and removed (no test files left behind — test framework wiring for this area is still a Phase-3+ backlog item, unchanged from the last two phases' notes).

## Phase 5 — AI layer (done)

- **The four jobs, exactly as spec'd**: `sector_classify.ts` (batched 20, zod-validated against a dynamic `z.enum(icp.sectors)`, one retry with an error-correction hint, fails open to `sector: null` on a second bad response rather than throwing — one bad batch can't kill a run), `pain-brief.ts`, `outreach-pack.ts`, `call-prep.ts` — all built on the Phase 1 `callModel()` wrapper, which already appends the spec's exact grounding suffix to every prompt.
- **`outreach-pack.ts` vs `call-prep.ts` — a real disambiguation needed doing**: the spec lists "outreach pack" and "call prep" as two of the "four jobs," but §8 (call script: opener/3 questions/2 objections/close) is explicitly part of the outreach pack, while §9 says a positive reply gets "a reply-prep brief from the evidence" — a different thing with a different input (evidence **plus the reply text**). `DECISION`: `outreach-pack.ts` generates the §8 call script as part of the pack (all five deliverables — email1-3, DM, call script — in one structured-JSON call, since they're genuinely one cohesive pack); `call-prep.ts` is the separate §9 reply-triggered brief. ## Phase 6 — Run orchestration + Console (done)

- **Secrets generated**: `WORKER_SECRET`, `CRON_SECRET` (`openssl rand -hex 32`, per the master spec's own instruction for generatable secrets) — added to `.env.local` (gitignored, confirmed before writing). - **`TICK_MS=8000`, not the spec's 45000ms default** — that default assumes Vercel; Netlify's standard synchronous function execution has a much shorter ceiling (~10s). `DECISION`, logged per the spec's own instruction to "log whether the deployment plan supports the chosen tick duration": 8s leaves real margin under Netlify's limit. The escape hatch the spec names (a small always-on worker) remains a `LIMITATION`/`V2 CANDIDATE` if this ever needs to change.
- **Task granularity simplified from the spec's 6 implied task types** (`discover|enrich|audit|score|ai|pack|send`) **to two**: `discover` (one per source×sector) and `process_candidate` (crawl+extract+audit+score+persist+pack, all for one candidate, in one task). `DECISION`, logged: fine-grained per-stage tasks would need many more claim/emit round-trips for no real resumability benefit at this scale — a candidate's pipeline is fast and sequential, and collapsing it into one task still gets independent retry-per-candidate (§8's actual requirement: "one dead website never kills a run"), which is verified working (see below). `send` is reserved, unused until Phase 9.
- **Atomic task claiming** (`task-queue.ts`): a single `UPDATE ... WHERE id IN (subquery) ... RETURNING` statement rather than `SELECT ... FOR UPDATE SKIP LOCKED` — the spec explicitly offers this as an alternative. Reasoning for why this is safe under Postgres's default READ COMMITTED isolation (EvalPlanQual re-checks the WHERE clause against committed data before a blocked UPDATE proceeds) is in the code comment. Retry: failed tasks under 3 attempts go back to `pending` for a later tick; at the cap they're marked `failed` permanently — verified live (see below), not just by code review.
- **Worker tick mechanism, concretely**: no `after()`. Two API surfaces call the same `runTick()`: `POST /api/agents/leads/runs/[id]/tick` (session-authenticated, polled by the admin's own browser tab every ~1.5s while a run is active) and `POST /api/agents/leads/worker` (`WORKER_SECRET`-gated, rejects requests carrying an `Origin` header — for the sweeper/future external scheduler, matching the spec's literal design for that route).
- **Console events**: `GET /api/agents/leads/runs/[id]/events?after=<cursor>` — polling, not SSE. `DECISION`, extending the Phase 0 Netlify-adaptation note: the spec's own documented SSE-failure fallback ("2 SSE failures → poll every 2s") is used here as the *primary* mechanism, since a long-held SSE connection surviving Netlify's standard function timeout for the spec's `STREAM_MAX_MS` (50s) is a real unknown on this host, not a solved problem. `RunConsole.tsx` (client component) drives one combined poll loop — tick, then fetch new events, then fetch run status — every ~1.5s, capped at 500 rendered feed lines client-side.
- **Sweeper** (`GET /api/cron/lead-sweeper`): `CRON_SECRET`-gated, disabled by default via `LEAD_SWEEPER_ENABLED` (ships disabled per spec §0). Finds `running` runs with a heartbeat older than 3 minutes and calls `runTick()` on each.
- **`MAX_CONCURRENT_RUNS=1`** enforced synchronously in `createRun()` — a second start attempt gets a clear Dutch 409 error, never a silent queue, matching the spec exactly.
