# Leads Agent — Decisions Log

Branch: `leads-agent`. Started 2026-08-13. Format: `ASSUMPTION` (undocumented choice, most conservative option, kept working), `LIMITATION` (honest reduced version, logged, moved on), `V2 CANDIDATE` (tempting extra, deferred).

## Phase 0 — Repo inventory (read before building anything)

Full inventory was done via a repo-exploration pass. Key findings that change how this feature is built vs. a blank-slate reading of the spec:

- **Hosting is Netlify, not Vercel.** `netlify.toml` exists and configures `functions = "functions"`, `publish = ".next"`. No `vercel.json`. `.vercel/project.json` exists but appears stale/unused. `ASSUMPTION`: build against Netlify's Next.js runtime. Netlify Functions have their own execution-time limits (background functions support up to 15 min on paid tiers vs. the default ~10s/26s synchronous limit) and Next.js's `after()` from `next/server` is a Vercel-optimized primitive with uneven support elsewhere. `LIMITATION`: I will not assume `after()` reliably schedules a next tick post-response on this host. The run/worker split (§8 of the spec) is built as: a client-side poller calls `/api/agents/leads/worker` repeatedly (every ~2s) while a run is `running`, each call claims and processes one bounded batch and returns. This keeps every invocation short and synchronous, sidestepping the Netlify background-function question entirely, at the cost of the run depending on a client (browser tab or the sweeper cron) staying around to keep ticking it forward — exactly the gap the spec's own sweeper design anticipates. The sweeper cron route restarts stale runs the same way regardless of who was ticking them.
- **This is not a blank slate — extend `MODULE D: LEAD-ENGINE` in `drizzle/schema.ts`, don't create a parallel schema.** Existing tables: `leads`, `leadEvents`, `prospectSources` (1:1 with leads — a design smell but out of scope to fix), `outreachTasks`, `outreachMessages` (unused by any UI today, but shaped like the spec's `messages` table), plus `agentRuns` (cost/usage logging per AI call — closest analog to `ai_usage`) and `settings` (has `outreachApprovalRequired`, `suppressionListDomains`, `suppressionListEmails` array columns — today's suppression mechanism). `ASSUMPTION`: `outreachMessages` becomes the `messages` table from §9 of the spec (extended with columns, not replaced); a dedicated `suppression` table is added because array columns on a singleton `settings` row can't carry `source_url`/`reason`/`created_at` provenance per §4 rule 1, and AVG rule 10 (`forget` leaves a one-way hash) needs a real table with its own primary key.
- **`lib/agents/prospector.ts` is an orphaned stub, not working prospecting.** It makes one raw Anthropic call asking the model to *invent* 3 companies as JSON — no real data source, `options.limit` is accepted but never used, `estimatedCost` is hardcoded rather than computed, and nothing in the app calls this function (no route, no cron, no UI button). This directly violates the master spec's absolute rule "never invent companies... every scoring signal is reproducible from stored evidence." `DECISION`: this file is replaced by the real OSM-first discovery pipeline; it is not extended, because extending a hallucination generator would mean shipping fabricated leads into a real leads table used by a real business. The model string it and its two siblings (`email-triage.ts`, `content-generator.ts`) use, `"claude-opus-4-7"`, is not a real current model id — flagged, not fixed in those two unrelated files (out of scope), but the new shared AI wrapper uses real current ids (`claude-haiku-4-5-20251001`, `claude-sonnet-5`).
- **No component library exists** — just three CSS utility classes (`.btn-primary`, `.btn-secondary`, `.input-field`) plus hand-rolled markup per page (`components/ui/Modal.tsx`, `ConfirmModal.tsx`, `Pagination.tsx`, `SearchFilterBar.tsx`, `Toast.tsx` are the only shared pieces). No dark mode is implemented anywhere (`ASSUMPTION`: do not introduce one for this feature — matching the spec's "reuse, don't introduce new tokens" instruction literally means staying in the existing light-only, `bg-gray-50` shell). `DECISION`: new shared primitives this feature needs and the app lacks (`DataTable`, `StatusBadge`, `StatCard`, `EmptyState`) are added to `components/ui/` in the exact visual idiom of the existing 5 files (same border/radius/spacing choices), since the spec explicitly allows new primitives "only when nothing fits, built in the style of their neighbours" — a live console feed and an evidence table are things nothing existing fits.
- **Auth has two roles only** (`user`, `admin`), enforced today only via one inline page-level check, never via a reusable helper or role-gated API route. `DECISION`: introduce `lib/auth-guard.ts` with a `requireAdmin()` helper (the spec's owner/admin gating collapses to `admin` here, since there's no `owner` role in this app) and use it on every new mutating route. `ASSUMPTION`: "owner or admin" in the spec = "admin" in this app.
- **No rate limiter exists anywhere.** `DECISION`: build a minimal in-DB token-bucket-style limiter (reusing the pattern of counting recent `auditLog`/`agentEvents` rows in a time window) rather than pulling in a new dependency — matches "reuse the repo's limiter" in spirit (there isn't one to reuse, so a small one is added under `lib/rate-limit.ts` and treated as the thing future features reuse).
- **Migration workflow**: no `drizzle/migrations/` folder exists; `db:push` (schema-diff push, no committed SQL) is the only workflow actually exercised so far. `ASSUMPTION`: continue with `db:push` rather than introducing generated migration files for this feature alone — switching the whole repo's migration strategy is out of scope of a single feature branch.
- **Missing local secrets**: `.env.local` has Postgres/Neon/Vercel-blob vars only — `ANTHROPIC_API_KEY`, `RESEND_API_KEY`, `NEXTAUTH_SECRET`, `INTAKE_API_KEY`, `GOOGLE_PLACES_API_KEY`, `KVK_API_KEY` are all absent locally (likely set in Netlify's dashboard for production, not synced to this checkout). Every adapter/AI call in this feature is written to disable itself gracefully and report via `doctor` when its key is missing, per spec — this was going to be necessary regardless, and is doubly necessary given the local environment already lacks most keys.

## Phase 1 — Foundation (done)

- **Migrations**: hand-written SQL (`drizzle/migrations/0001_leads_agent_foundation.sql`), applied via `psql` directly against `$DATABASE_URL` in a single transaction, rather than `drizzle-kit push` (interactive, hangs with no TTY in this environment) or `drizzle-kit generate` (had no baseline snapshot, so it tried to `CREATE TABLE` every pre-existing table). Applied and verified live — see the table/column listing run after. `db:push`/`db:generate` remain broken for non-interactive use in this repo; a real fix (baseline snapshot + committed migration history) is a `V2 CANDIDATE`, out of scope for a single feature branch. `LIMITATION`: `drizzle/migrations/` is `.gitignore`d in this repo (the `db:push` workflow treats `schema.ts` as the source of truth, migrations as throwaway) — the SQL file stays local-only and is **not** part of this commit; `schema.ts`/`schema-leads.ts` are what actually ships. Anyone continuing this branch on a different checkout or against a fresh database needs to regenerate the equivalent SQL from the schema diff first — it is not tracked anywhere in git.
- **New tables** live in `drizzle/schema-leads.ts` (re-exported from `drizzle/schema.ts` via `export * from "./schema-leads"` at the bottom) to keep `schema.ts` from crossing ~900 lines. `leads`, `outreachMessages`, and `agentRuns` got additive columns in place rather than parallel tables.
- **`leads.email` is now nullable** (was `NOT NULL`) — required to let the agent create a lead with only a phone/contact-form channel, per §6 of the spec ("at least one reachable channel", not "an email"). Fixed the two pre-existing pages (`leads/page.tsx`, `leads/[id]/page.tsx`, `LeadCard.tsx`) that assumed `email` was always a string.
- **Auth**: added `lib/auth-guard.ts` (`requireAdmin()`) — the first reusable role-gate helper in the repo. "Owner or admin" in the spec collapses to `admin` here (no `owner` role exists).
- **Rate limiter**: added `lib/rate-limit.ts`, a minimal DB-backed limiter counting recent `audit_log` rows in a time window — none existed before. Not yet wired into any route (nothing rate-limited enough to need it in Phase 1); will be used starting Phase 6 (run starts) and Phase 8 (exports).
- **AI wrapper**: `lib/agents/anthropic-client.ts` replaces the triplicated client-init/JSON-regex/agentRuns-logging boilerplate in `prospector.ts`/`email-triage.ts`/`content-generator.ts` (not edited themselves — out of scope). Uses real current model IDs (`claude-haiku-4-5`, `claude-sonnet-5`) via `MODEL_CHEAP`/`MODEL_SMART` env vars, computed cost from real per-model USD pricing (Sonnet 5 $3/$15 per MTok, Haiku 4.5 $1/$5 — Anthropic pricing catalog, cached 2026-06-24), and logs every call to `agent_runs` (reused as the `ai_usage` table via new `lead_run_id`/`purpose` columns). `ASSUMPTION`: USD pricing is compared directly against `AI_DAILY_BUDGET_EUR` with no currency conversion — conservative (USD ≳ EUR most of the time) rather than pulling in an FX dependency for a soft budget guard; revisit if the gap widens.
- **Config store**: `lib/leads-agent/config.ts` — versioned (`lead_agent_config` table, append-only rows per key+version, `isActive` flag marks current), with the spec's §3/§7 ICP and rubric defaults hard-coded as the fallback when no row exists yet. `saveConfig`/`restoreConfigVersion` both write an `audit_log` entry (`lead_config_updated`), matching the repo's existing audit convention.
- **Doctor endpoint**: `GET /api/agents/leads/doctor` (route logic in `lib/leads-agent/doctor.ts` so the Console page can call it directly without an internal HTTP round-trip). Checks: DB connectivity, required/optional env vars (optional ones degrade to amber, never red), AI budget spent-today vs. cap, suppression table reachability, stale/stuck runs (heartbeat >3 min — same threshold the not-yet-built sweeper will use), and the outbound kill-switch state.
- **Nav**: added "Leads Agent" (🎯, `/leads/agent`) to `lib/navigation.ts` with a new `adminOnly` flag, threaded through `Sidebar`/`MobileNav` (previously unfiltered — first role-gated nav item in the app) via a `role` prop from the dashboard layout. Added a breadcrumb entry in `Navbar.tsx`'s `ROUTE_LABELS` (had to be inserted *before* the existing `/leads` entry since the lookup is a `startsWith` scan in insertion order). `DECISION`: this lives under `/leads/agent` — a fourth, clearly-scoped entry next to the existing "Leads" and "Prospecting" nav items — rather than reusing either of them, since neither's existing page/route structure fits six tabs and a live console.
- **Route shell**: `app/(dashboard)/leads/agent/{layout,page}.tsx` + one folder per tab (Console, Leads, Outbound, Runs, Instellingen, Health). Layout does the admin gate (`notFound()` for non-admin — matches the spec's "404 from routes" instruction). Console is real and functional (renders the doctor report live); the other five tabs are honest placeholders stating what's still to come, not stubs pretending to be finished. Instellingen additionally renders the current ICP/rubric/threshold config read-only (editing UI is Phase 11).
- **New shared UI**: `components/leads-agent/AgentTabs.tsx` (client component for active-tab highlighting) — the one new primitive this phase needed; everything else reused `.btn-primary`/`.input-field`/existing card/table markup.
- **Verification**: `npx tsc --noEmit` clean, `npm run build` succeeds (all 6 new routes registered, no route-type errors). `npm run lint` fails — **pre-existing**, unrelated to this branch: no ESLint config file exists anywhere in the repo (`npm init @eslint/config` was never run). Logged as `LIMITATION`, not fixed (out of scope — a repo-wide tooling gap, not something this feature introduced).
- **Not yet exercised end-to-end**: the doctor endpoint and config store are live against the real database (confirmed via the build + a manual schema check), but no automated test suite exists in the repo for this area yet (`vitest`/`playwright` are configured for the app generally, no leads-agent-specific tests written yet — planned starting Phase 3, once there's real crawl/scoring logic worth testing).
